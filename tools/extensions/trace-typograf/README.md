# Trace Typograf — браузерное расширение

Портирует движок русской типографики из Figma-плагина «Trace Typograf»
(`tools/figma-plugins/typograf/`, конкретно — из его «чистой» копии без
Figma API, `scripts/lib/typograf.js`) в кнопку, которая работает прямо в
текстовых полях сайта.

v1: попап с одной кнопкой «Расставить типограф», действует на
сфокусированное текстовое поле целиком. Площадки — **Taptop** (taptop.pro)
и **Tilda** (tilda.cc).

## Установка (режим разработчика)

1. `chrome://extensions` → включить «Режим разработчика».
2. «Загрузить распакованное расширение» → выбрать эту папку
   (`tools/extensions/trace-typograf/`).
3. Открыть редактор на taptop.pro или tilda.cc, кликнуть в текстовое поле,
   нажать иконку расширения → «Расставить типограф».

## Структура (1 функция = 1 файл)

- `src/core/rules/` — чистый текстовый движок, порт `scripts/lib/typograf.js`
  из основного репозитория, функция в функцию, файл в файл. Никакой
  зависимости от DOM/browser API — можно гонять в Node (см. проверку ниже).
- `src/dom/` — DOM-слой: определение редактируемого элемента
  (`isEditableElement`/`getEditableRoot`), Myers-дифф старого/нового текста
  (`myersDiff`/`diffToHunks`) и точечное применение только изменившихся
  кусков через `Selection`/`execCommand('insertText')`
  (`applyHunksToContentEditable`/`applyHunksToInput`) — это то, что сохраняет
  жирный/курсив и прочее форматирование внутри поля, вместо того чтобы
  перезаписывать весь текст целиком.
- `src/content/` — content-script: следит за фокусом на странице
  (`trackFocusedEditable`) и слушает сообщение от попапа (`contentEntry`).
- `popup/` — UI кнопки. Не бандлится, простой classic `<script src>`.
- `build/build.js` — склеивает `src/core/rules/` + `src/dom/` + `src/content/`
  в один `dist/content.js` (порядок файлов задан явно внутри скрипта).
  **Правь только файлы в `src/`**, `dist/content.js` — сгенерированный
  артефакт.

## Пересборка после правки src/

```bash
node tools/extensions/trace-typograf/build/build.js
```

`--dry-run` — посчитать без записи.

## Как движок сверен с оригиналом

Логика в `src/core/rules/` — дословный порт `scripts/lib/typograf.js`.
Сверка прогоном обоих движков на одинаковых строках дала побайтовое
совпадение (включая места с НБСП, которые визуально неотличимы от обычного
пробела — при следующей правке `constants.js` проверяй `NBSP` именно по
кодпойнту `U+00A0`, а не глазами: обычный пробел выглядит идентично, но
собьёт всю расстановку молча).

## Про домен/путь и устройство Taptop

Редактор Taptop живёт не на домене `taptop.pro`, а по **пути**
`/-/cms/v1/mosaic/*` на произвольном хосте (у каждого проекта свой
поддомен вида `site-XXXXX.taptop.site`) — подсмотрено в соседнем рабочем
расширении пользователя (`~/Documents/Расширения/taptop-helper`,
инструменты мультивыделения слоёв и автопубликации). `manifest.json` здесь
использует тот же паттерн `*://*/-/cms/v1/mosaic/*`.

Живьём проверено 2026-08-10 (`site-03979.taptop.site`):

- Холст рисуется внутри `<iframe id="tt-iframe">`, но это не важно для
  текстовой правки — сам текстовый виджет в покое это плоский
  `<div class="text …">` БЕЗ `contenteditable` вообще (0 штук на странице
  в состоянии покоя). При двойном клике для входа в редактирование Taptop
  открывает поверх холста, но **в верхнем документе (не в iframe)**,
  оверлей на Draft.js (`public-DraftEditor-content`,
  `public-DraftStyleDefault-block` — фирменные классы facebook'овского
  Draft.js) — это и есть `document.activeElement` в момент правки,
  `contenteditable="true"` стоит прямо на нём.
- `document.execCommand('insertText', …)` из ISOLATED-мира это поле
  реально меняет: Draft.js слушает нативное `beforeinput`-событие и
  сверяет DOM с моделью — тем же способом он подхватывает нативную
  проверку орфографии браузера. Тире/кавычки-ёлочки/многоточие сохраняются
  корректно и после выхода из редактирования.
- **НБСП — исключение.** Taptop хранит "неразрывность" не как символ
  U+00A0 в тексте, а как свой виджет «Прерывание» (панель справа при
  редактировании), сериализуемый в `<span style="white-space:pre">`.
  Литеральный НБСП, вставленный через `execCommand`, визуально стоит на
  месте, пока фокус в поле, но при выходе из редактирования Taptop
  пересобирает содержимое из своей модели — перенос слова реально ломается
  (не косметика, а settled-баг).

  Решение — `src/platform/applyTaptopNoBreakRuns.js`: вместо вставки НБСП
  для каждой такой пары слов программно выделяется Range именно на этой
  паре (Selection API) и кликается их родная кнопка «не переносить»
  (`.tt-editor-panel__white-space .tt-button-group` — вторая из двух,
  первая, активная по умолчанию, — «переносить можно»; появляется в
  панели только когда в Draft.js есть непустое выделение, поэтому после
  каждого `sel.addRange()` функция ждёт её в DOM). Правка идёт через их же
  React-обработчик — переживает выход из редактирования, как и ручной
  клик. `taptopQuirks.js` следом просто не даёт `execCommand` вставить сам
  символ НБСП (та часть текста уже обработана кнопкой), вся остальная
  типографика (тире/кавычки/многоточие) идёт как обычно.

Тот же `taptop-helper` работает с внутренним состоянием редактора
(MobX-стор, буфер обмена, дерево слоёв) через
`window.rspackChunktaptop_design_editor` и `content_scripts[].world: "MAIN"`
— но это для операций уровня слоёв (копировать/удалить/вставить), не для
правки текста внутри поля; нашему коду это не понадобилось.

## Автовход/автовыход из редактирования (Taptop)

Найдено вживую 2026-08-10 через `window.rspackChunktaptop_design_editor`
(та же техника, что у `taptop-helper`) — `req(87621).A` (UIState) отдаёт
`isTextEditorMode`/`setTextEditorMode(bool)`. Synthetic `dblclick`
(с `metaKey: true` и без) по элементу на холсте не входит в редактирование
— скорее всего, дело в `event.isTrusted` (синтетические события им не
считаются). Их API — рабочий путь, DOM-события — нет.

Проблема: `chrome.runtime.*` недоступен в content-script'ах с
`"world": "MAIN"`, а `window.rspackChunktaptop_design_editor` недоступен
из ISOLATED-мира, где живёт весь остальной код расширения. Решение — два
content-script'а и канал между ними через `CustomEvent` на `document`
(общий для обоих миров):

- `src/platformMain/taptopMainBridge.js` → `dist/taptop-main-bridge.js`,
  отдельный content-script с `"world": "MAIN"` — слушает
  `trace-typograf:taptop-api`, дёргает `A.setTextEditorMode`, отвечает
  `trace-typograf:taptop-api-result`.
- `src/platform/taptopApiBridge.js` (часть обычного `dist/content.js`,
  ISOLATED-мир) — `callTaptopApi('enter-edit' | 'exit-edit')`, шлёт запрос
  и ждёт ответ с таймаутом.
- `src/platform/enterTaptopEditModeIfNeeded.js` — используется, когда по
  сообщению от попапа `document.activeElement` не редактируем: просит
  войти в редактирование текущего выбранного слоя и ждёт, пока
  `document.activeElement` реально станет Draft.js-полем.
- `src/platform/exitTaptopEditing.js` — то же самое в обратную сторону,
  после применения правок; `blur()` — запасной путь, если API не сработал.

Важно: автовход пробуется, только если `window === window.top`
(`contentEntry.js`) — сам API и реальный текстовый редактор живут в
верхнем документе, не в `#tt-iframe` (см. выше).

## Применение ко всему контейнеру (Taptop)

Аналог `collectTextNodes()` из Figma-плагина (там — рекурсивный обход
`children` по дереву Figma-узлов, собирающий все TEXT-ноды выделения).

**Первая версия обходила их `E.tree`** (MobX-дерево слоёв, `req(36945).A`,
узел считался текстовым по записи `["text", …]` в `data`) и переносила
суффикс `_N` (индекс повторения) с корня выделения на каждый найденный id.
**Оказалась в корне неверной для повторяющихся списков/каруселей**
(`List`/`Block List`) — проверено вживую 2026-08-10 на реальном `Block
List` с `Item1`/`Item2`: `E.tree` хранит только ОДНО определение шаблона
повтора (`i0xqkzv0f`), без единого намёка на то, сколько раз он реально
отрисован. Обход всегда находил только первую итерацию (суффикс `_0`,
Item1) и молча пропускал остальные (Item2 и далее) — не баг в переносе
суффикса, а принципиальный потолок: то, чего в дереве физически нет,
оттуда не достать.

**Текущая версия обходит панель слоёв** (`src/platform/
collectTaptopTextRows.js`) — она рисует РЕАЛЬНЫЙ DOM, поэтому знает
истинное число повторов, в отличие от дерева данных. Глубина строки —
класс `pd-N` на `.tt-layers__item`; текстовая строка — иконка с классом
`tt-icon--name-medium-widgets-text` (обе детали проверены вживую
2026-08-10). Обход идёт от строки с классом `is-selected` (то, что сейчас
выбрано) вниз по DOM-порядку строк, пока не встретится строка с
`depth <= depth корня` — это и есть конец его поддерева. **Клик по
найденной строке (`row.click()`, тот же приём, что `taptop-helper`
использует для `.tt-layers__item`) одновременно и находит, и ВЫБИРАЕТ её**
— с правильным id/суффиксом для этого конкретного повторения; отдельный
шаг «select по id» через их API (`A.setSelected`) больше не нужен.

⚠️ **`A.setSelected(id)` с выдуманным/несуществующим id роняет весь
редактор** (`Error: Узел должен существовать`, страница показывает «Что-то
пошло не так») — проверено вживую 2026-08-10 при переборе `id0, id1, id2,
id3` вслепую. Обходить дерево/перебирать id "на удачу" через их API
нельзя, только клики по реально существующим DOM-строкам панели.

`src/platform/applyTypografToTaptopSelection.js` — для каждой найденной
строки: `row.click()` → `enterTaptopEditModeIfNeeded()` →
`applyTypografToElement` → (если не менялось) `exitTaptopEditing`. Один
выбранный текстовый виджет без вложенных — тоже проходит этот путь, просто
список из одной строки (сам корень, если он текстовый).

## ⚠️ Инцидент 2026-08-10: расширение стирало слова

Живьём поймано на реальном контенте: часть слов («и чувствуют», «с
ребёнком») пропадала из текста после прогона — не косметика, реальная
потеря данных (пользователь откатил через `Cmd+Z`). Причина — цепочка
из двух вещей:

1. Кнопка «не переносить» — тумблер. Если для какой-то пары слов стиль
   уже был включён (с прошлого прогона или руками), наш код всё равно
   выделял её и жал кнопку заново — то есть ВЫКЛЮЧАЛ его, и это меняло
   DOM способом, который не был учтён дальше.
2. `applyHunksToContentEditable` применяет остальные правки (тире,
   кавычки) по офсетам, посчитанным заранее относительно `oldText` —
   если между расчётом и применением текст в поле уже разъехался с
   `oldText` (из-за пункта 1), офсеты указывают не туда, и
   `execCommand('insertText', …)` подменяет случайный кусок текста рядом
   с правильным местом — так пропадают целые слова, не потому что их
   "удаляли", а потому что диапазон замены съехал.

Фикс — оба конца проблемы: `applyTaptopNoBreakRuns.js` теперь проверяет
`buttons[1].classList.contains('tt-button--state-active')` ПЕРЕД кликом и
не трогает уже включённый стиль повторно; `applyTypografToElement.js`
сверяет `getElementText(root)` с `oldText` непосредственно перед
применением обычных hunks и, если текст успел разойтись, остальные
правки просто не применяет (лучше недоправить, чем стереть слова). Плюс
ещё одна такая же проверка живости `root` (`document.contains`) прямо
перед самим применением hunks — и `try/catch` вокруг него: если Draft.js
всё-таки успел заменить узел поля в процессе, `addRange()` кидает
исключение, и без catch это обрывало `applyTypografToElement` на середине,
пропуская авто-выход из редактирования.

### Второй раунд той же болезни: `<br>` внутри текста

Тот же класс бага, другой триггер — текст с ручным переносом строки
(`<br>` прямо в разметке, Taptop вставляет его при Shift+Enter). `<br>` не
даёт ни одного символа в `textContent` — "слово<br>слово" читалось
движком как слитное "словослово" безо всякого пробела, вся арифметика
смещений после такого места съезжала так же, как в основном инциденте
выше, — и снова стирало соседние слова.

Первая попытка фикса — учитывать `<br>` как "виртуальный пробел" прямо в
карте офсетов (`walkEditableDom.js`, с этим же именем файл существовал
недолго, потом удалён) — не прижилась: Selection/Range на границе такого
виртуального символа вели себя непредсказуемо в Draft.js, и потеря текста
повторилась ещё раз тем же вечером.

**Финальное решение — `src/dom/normalizeBrToSpace.js`**: вместо попытки
научить диф понимать `<br>` как особый случай, он физически заменяется на
настоящий текстовый пробел ДО того, как что-либо считается —
`applyTypografToElement.js` вызывает это первым делом. Важно: замена идёт
через `Selection` + `execCommand('insertText', ' ')` (тот же путь, что и
все остальные правки), а НЕ прямой мутацией DOM (`node.replaceWith(...)`)
— Draft.js реконсилит свою модель по нативным input-событиям от
`execCommand`, но не видит произвольную мутацию DOM в обход них; первая
черновая версия этого файла делала именно `replaceWith` и от этого модель
Draft.js расходилась с DOM. После нормализации `getElementText.js` и
`textNodeOffsetMap.js` — простые, ничего не знают про `<br>`, как и до
всей этой истории.

**Побочный эффект (осознанный, по просьбе пользователя):** принудительный
перенос строки на месте `<br>` пропадает — текст течёт обычным потоком,
перенос дальше целиком на усмотрение вёрстки/ширины блока.

## Попап сам обновляет код во вкладке (снято 2026-08-19)

Chrome не переинжектит content script в уже открытые вкладки после
перезагрузки расширения — там продолжает жить код, загруженный при
открытии страницы. Раньше это лечилось просьбой нажать Cmd+R, и вопрос «а
точно ли во вкладке новый код» съел несколько итераций отладки подряд:
правка на диске есть, поведение старое, и по одному сообщению в попапе это
неотличимо от несработавшего фикса.

Теперь `popup.js` при каждом нажатии кнопки:

1. шлёт `PING_BUILD` и получает штамп сборки content script'а (отвечает
   только верхний кадр — первый `sendResponse` выигрывает, и ответ из
   случайного iframe всё бы испортил);
2. сравнивает со своим (`dist/build-stamp.js`, пишется тем же
   `build/build.js`, что и `BUILD_STAMP` внутри бандла);
3. при расхождении или молчании впрыскивает `dist/taptop-main-bridge.js`
   (world: MAIN) и `dist/content.js` (all frames) через
   `chrome.scripting.executeScript` и продолжает работу.

Повторную инжекцию оба файла переживают: `window.__traceTypografLoaded` в
изолированном мире и `window.__traceTypografBridgeLoaded` в MAIN — второй
слушатель не регистрируется. Требует разрешения `scripting` в манифесте;
после его добавления расширение нужно перезагрузить один раз (разрешения
читаются при загрузке), дальше правки доезжают сами.

## Gotcha при разработке: «Reload» расширения не долетает до открытой вкладки

После клика «Reload» на карточке расширения в `chrome://extensions`
content-script в уже открытых вкладках остаётся привязан к старому
контексту — обычный `Cmd+R` иногда не долетает (SPA/bfcache), сообщение из
попапа падает с `chrome.runtime.lastError`, хотя в консоли на вкладке
скрипт как будто есть (можно увидеть его дублирующимся в списке контекстов
DevTools Console — выпадашка «top» вверху панели). Лечится закрытием
вкладки целиком и открытием заново той же ссылкой — не просто перезагрузкой.

## ⚠️ Инцидент 2026-08-19: «уже без замечаний» вместо неразрывного пробела

Расширение на Taptop отчитывалось «Уже без замечаний — менять нечего» на
тексте, где движок явно должен был поставить НБСП («собирается из
нескольких» → неразрывность после «из»). Правила были ни при чём — прогон
`src/core/rules/*` в Node на той же строке честно возвращал НБСП.

Цепочка: клик по иконке расширения забирает фокус у страницы → Draft.js на
blur сносит редактор Taptop (правая панель переключается на «Настройки»)
→ `getLastFocusedEditable()` продолжает отдавать **оторванный от документа**
узел → `applyTaptopNoBreakRuns` не может построить на нём Range и тихо
выходит в ноль → `getElementText` у оторванного узла всё ещё возвращает
старый текст, поэтому защита «текст изменился во время обработки» не
срабатывает → литеральный НБСП на Taptop вырезается (`taptopQuirks.js`) →
`hunks` пустой → `changed: false, reason: 'no-change'` → попап пишет
«уже без замечаний».

Две правки, обе нужны:

1. **`src/content/contentEntry.js` — корень.** На Taptop с выбранным слоем
   ветка «войти в редактирование самому» (`applyTypografToTaptopSelection`)
   стала ОСНОВНОЙ, а не запасной. Раньше она включалась только при пустом
   `focusedTarget`, и любой живой `contenteditable` перехватывал управление
   раньше неё. Первая попытка чинить это проверкой «жив ли узел»
   (`isEditableElement(el) && document.contains(el)`) оказалась
   недостаточной: узел редактора Draft.js остаётся в DOM и остаётся
   `contentEditable` даже после выхода Taptop из режима редактирования
   текста — он жив, но панель «Прерывание» на нём уже не поднимется.
   Надёжного DOM-признака «сейчас идёт редактирование» нет
   (`.tt-editor-panel` появляется только при непустом выделении ВНУТРИ уже
   открытого редактора), поэтому состояние не угадывается — вход делается
   всегда через их API: `setTextEditorMode(true)` идемпотентен.
2. **Честные причины отказа вместо одного `'no-change'`.**
   `applyTaptopNoBreakRuns` → `{ applied, failed }`,
   `applyTypografToTaptopSelection` → `{ changed, count, visited, entered,
   failed }`, попап различает `'nobreak-failed'` (пары нашлись, кнопку
   нажать не вышло) и `'enter-failed'` (текст нашёлся, войти в
   редактирование не удалось). Раньше «править было нечего» и «нашёл пары, но не
   смог нажать кнопку» отдавали один и тот же `'no-change'` — расширение
   рапортовало об успехе, ничего не сделав. Теперь провал виден в попапе
   отдельным текстом.

Диагностическая последовательность, которой это поймано (полезна и
дальше): прогнать правила в Node на реальной строке → убедиться, что
`.tt-editor-panel__white-space .tt-button-group` жив и панель поднимается
на голый `selectionchange` → повторить весь цикл руками из консоли. Ручной
прогон проставлял `<span style="white-space: pre">` без единой ошибки —
это и локализовало поломку до точки входа.

## ⚠️ Инцидент 2026-08-19 (продолжение): грязное состояние редактора

Симптомы, с которых начался разбор, звучали как два разных бага:

1. Выбираешь секцию — «в выбранном слое не нашли текстовых слоёв».
   Перезагружаешь страницу, запускаешь снова — всё срабатывает. Идёшь к
   следующему блоку — снова не находит.
2. Запускаешь на уже поправленном тексте — расширение заходит в
   редактирование, подвисает, из режима правки не выходит и отвечает, что
   текста не нашло.

Причина у обоих одна. **Режим редактирования текста у Taptop — глобальное
состояние редактора, а не свойство нашего прогона.** Пока он открыт, клик
по строке в панели слоёв не переключает выбранный слой. Цикл по слоям
делал `continue` при неудачном входе, НЕ закрыв редактор, — и всё после
этого слоя отваливалось каскадом. Хуже, что открытый редактор переживал
конец работы и отравлял СЛЕДУЮЩИЙ запуск: он не находил слои, и лечила
только перезагрузка страницы (то самое «несколько раз обновлю — и он всё
исправляет»).

Что сделано в `applyTypografToTaptopSelection.js`:

- `exit-edit` ПЕРЕД обходом — чистый старт не предполагается, а
  обеспечивается;
- `exitTaptopEditing` после КАЖДОГО слоя безусловно, а не только когда
  были правки (exit идемпотентен);
- весь цикл в `try/finally` с `exit-edit` в `finally` — исключение на
  середине больше не оставляет редактор открытым;
- одна повторная попытка входа через принудительный `exit-edit`: самая
  частая причина неудачи — редактор, оставшийся от предыдущего слоя.

Отдельно: `applyTaptopNoBreakRuns` теперь считает `already` (пара уже была
неразрывной) отдельно от `applied`. Раньше повторный прогон по чистому
тексту рапортовал «Готово — типографика расставлена», не тронув ни одного
символа.

**Числа прогона видны в самом попапе** — «Слоёв с текстом: N, открыто: M,
изменено: K, уже было неразрывно: L, не удалось: F. Сборка ‹дата›» — и
дублируются в консоль. Пользователь читает результат в окошке, а не в
DevTools; без цифр «уже без замечаний» и молчаливый провал выглядят
одинаково. Штамп сборки в баннере при загрузке отвечает на вопрос «а
свежий ли код во вкладке» — Chrome кеширует content script, и после «⟳» в
`chrome://extensions` вкладку надо перезагрузить.

## Известные ограничения v1

- Правка идёт через `document.execCommand('insertText', …)` — устаревший, но
  до сих пор поддерживаемый Chrome API; выбран специально, потому что он
  порождает настоящие trusted input-события, на которые реагируют
  React/Vue-редакторы (прямая запись в `.value`/`.textContent` для них
  невидима и откатывается следующим ре-рендером).
- `all_frames: true` в манифесте — на случай, если Tilda рисует холст
  внутри iframe (Taptop, как выяснилось, — нет, там текстовое поле в
  верхнем документе); не проверялось на живой Tilda.
- Символ, который правило заменяет ровно НА границе форматирования (тире
  вместо дефиса, который был первым символом внутри `<b>`), может оказаться
  СНАРУЖИ тега после правки — диф патчит текст по точным старым офсетам, а не
  «видит» разметку, поэтому новый символ ложится ровно туда же, где был
  старый, даже если старый был первым символом жирного фрагмента. Проверено
  в тесте (`Скидка 20% для новых клиентов <b>- успей купить!</b>` →
  `— <b>успей купить!</b>`) — редкий и чисто косметический случай, не портит
  ни текст, ни остальное форматирование.
- Правило про перенос строки: диф считается по `textContent`/`.value`, без
  синтетических `\n` на границах блочных элементов (в отличие от
  `innerText`) — офсеты честно совпадают с реальными Text-нодами, но
  типографика не видит разрыв абзаца между соседними `<div>`/`<p>` внутри
  одного поля. `<br>` — отдельный случай, не подпадает под это ограничение:
  он заменяется на обычный пробел ДО расчёта (`normalizeBrToSpace.js`, см.
  выше «Второй раунд той же болезни»), поэтому перенос строки на его месте
  пропадает, а не просто «не виден» диффу.
