# Project Overview

**Trace Logos** — веб-каталог SVG/PNG-логотипов российских и международных брендов: просмотр, поиск, редактирование цветов, экспорт.

**Stack:** Vanilla JS ES Modules, без фреймворка и без build step для клиента. Статический сайт, `server.js` — dev-сервер.

**Data flow:** `logos/manifest.json` → `logos/categories/*.json` → элементы логотипов → `assets/logos/svgs|pngs/`.

Item: `name`, `tags`, `figma` (путь компонента Figma), `file`, `variants[]`, `ecosystem`. Опционально `alt_name` / `alt_name_en` — второе искомое имя бренда («Сбербанк» для Сбер): `build-seo-pages.js` рендерит «Имя (Алиас)» в title/H1/OG и `alternateName` в JSON-LD. Добавляй, когда бренд широко ищут под другим именем. Опционально `title_head` — ручной RU-зачин title и OG-title вместо «Логотип {имя}» (пример: ВКонтакте → «Логотип и значок ВК (ВКонтакте)»); `build-seo-pages.js` подставляет его перед « в векторе — скачать…», H1 и EN не меняются.

**Возможности:** каталог по категориям и экосистемам (Yandex, Sber, VK, Google…); поиск с авто-переключением раскладки RU↔EN (`search.js`); редактор цветов — HSV-пикер, undo/redo, история (`color.js`, `picker.js`, `color-math.js`); экспорт SVG/PNG/буфер/ZIP/Figma-ready SVG (`export.js`); виртуальный скролл (`virtual.js`); форма предложения логотипа → Supabase Edge Function (`suggest.js`).

**JS-модули:** `main.js` (оркестратор), `data.js`, `color.js`, `color-math.js`, `picker.js`, `export.js`, `search.js`, `virtual.js`, `suggest.js`, `seo.js`, `help.js`, `utils.js`.

**UI:** левый сайдбар (категории/экосистемы, на мобильном за бургером); основная область — сетка карточек по секциям категорий; панель деталей по клику на карточку (превью, варианты, редактор цветов, экспорт); один поиск в шапке по всем категориям.

**Виртуальный скролл:** секции вне viewport (±900px overscan) размонтируются, высота контейнера сохраняется; при скролле секции монтируются и лениво грузят картинки.

## Logo variants

`item.variants[]` — дополнительные файлы того же логотипа. Вариант `_original` (= `item.file`) `main.js` добавляет в начало при рендере; в JSON его нет.

Три формата записи:
- `{ "type": "full"|"full_en"|"png"|"svg", "file": "..." }` — известный тип; `TYPE_LABELS` в `main.js` даёт подпись. Тип задаёт форму карточки: `full`/`full_en` — широкая, остальные — квадратная.
- **Каждый `*-full.ext` получает явный `"type": "full"`** (или `full_en`) — даже если `viewBox` квадратный (монета, значок). Не подменять на `"type": "svg"` ради формы. Свой `labelKey`/`label` добавляется поверх `type`, а не вместо.
- `{ "label": "Old Icon", "file": "..." }` — без типа, подпись как есть; форма по имени файла (`-full.ext` → широкая, иначе квадратная, `isFullFile`).
- `{ "labelKey": "old-icon", "file": "..." }` — ссылка в `logos/labels.json` (`{ "<key>": { "label", "label_en"? } }`), общий словарь одноразовых подписей (праздничные ресскины, старые логотипы, альт-версии). Для новой одноразовой подписи предпочитай его inline-`label`/`label_en`: переиспользуй существующий ключ или добавь новый (файл отсортирован по ключу). `resolveCategoryLabels()` (`scripts/lib/labels.js`, зеркало в `js/data.js`) сразу после чтения категории заполняет `v.label`/`v.label_en`, остальные модули читают их как обычно. `test-data.js --pre` роняет сборку на `labelKey` без записи.

Итоговая подпись: `v.label ?? TYPE_LABELS[v.type] ?? v.type ?? ''`.

**Бренд без официальной квадратной иконки:** `file` — официальный горизонтальный ассет, `thumb` — квадратная замена (только плитка сетки; не скачиваемый вариант, не в `variants[]`); скажи об этом в `about`. `main.js` берёт `item.thumb ?? item.file` для плитки и показывает `#detail-noicon`, когда задан `thumb`. Поля `unofficial` нет. Образцы: T-ID в `story-i-podpiski.json`, Альфа Pay в `platezhi-i-karty.json`.

## Adding a new logo

1. SVG в `assets/logos/svgs/` (или PNG в `assets/logos/pngs/`).
2. Запись в подходящий `logos/categories/*.json`.
3. Обязательно: `name`, `tags`, `figma`, `file`, `dateAdded` (`YYYY-MM-DD`), `about`, `desc`, `brandUrl` (официальный сайт/бренд-гайд — питает `Brand.sameAs` и `ImageObject.license` в JSON-LD). Опционально: `dateModified`, `variants[]`, `ecosystem`, `thumb`. Без `dateModified` страница показывает «Добавлено» по `dateAdded`, с ним — «Изменён»; эти поля — единственный источник видимой даты, JSON-LD и sitemap (билдеры не выводят даты из Git/mtime/даты сборки). **`about`/`desc` обязательны:** `about` — текст SEO-страницы, `desc` — `<meta description>`. `test-data.js --pre` гейтит `name`/`tags`/`figma`/`file`/`dateAdded`/`dateModified`; отсутствие `about`/`desc` он не ловит, но пропускать их нельзя. У каждого не-`comingSoon` логотипа `about` есть — так и держать.
4. Новый ключ `ecosystem` сначала добавить в `logos/ecosystems.json` (`build-all.js` ключи не создаёт, только страницы для существующих).
5. `npm run build`. Отдельные скрипты для рутинного изменения контента руками не запускать (шаги забываются и идут не по порядку); `npm run build -- --dry-run` — превью.
6. Про WebP-превью думать не надо: `build-webp-previews.js` делает превью каждому логотипу, PNG и SVG.

**Форма предложения логотипа:** модалка шлёт данные (имя, URL или файл) POST на Supabase Edge Function `WORKER_URL` из `js/suggest.js` (`…/functions/v1/suggest`, проект `wezryybxxwicysnbmhkz`), код в `supabase/functions/suggest/index.ts`. Cloudflare Worker `brand-icons-sanitizer` выведен — не упоминать как живой.

**Валидация файлов:** SVG проходит `supabase/functions/_shared/svg-sanitizer.ts` (whitelist элементов/атрибутов, вырезает `<script>`/обработчики). Растр (`png`/`jpg`/`jpeg`/`webp`) проверяется по whitelist расширений и по magic bytes (`RASTER_SIGNATURES` в `suggest/index.ts`); иное расширение или несовпадение байтов → 422 до Telegram.

**Telegram-бот:** токен живёт ТОЛЬКО как секрет Supabase `BOT_TOKEN` — не коммитить и не вставлять открытым текстом. Если описание бота захвачено спамом (токен утёк): @BotFather → `/mybots` → API Token → Revoke current token; `npx supabase secrets set BOT_TOKEN=<new> --project-ref wezryybxxwicysnbmhkz` (редеплой не нужен); очистить Description и About; включить Two-Step Verification и проверить Settings → Devices.

# Emoji Section

Каталог эмодзи — `/emoji/`, тот же `main.js`, CSS и пайплайн, что у логотипов.

**Data flow:** `emoji/manifest.json` → `emoji/categories/*.json` (9: smileys-emotion, people-body, animals-nature, food-drink, travel-places, activities, objects, symbols, flags) → `assets/emoji/pngs/`.

**PNG:** `assets/emoji/pngs/<vendor>/<slug>_<hex-codepoints-через-дефис>.png`. Основной вендор — всегда **apple** (160×160, кроп по bbox контента, пропорции сохранены — fit, не stretch); Google — `google/…` (с emojigraph.org). Ведущие нули обязательны: `grinning-face_1f600`, ZWJ `ballet-dancer_1f9d1-200d-1fa70`, keycap `hash_0023-fe0f-20e3` / `keycap_star_002a-fe0f-20e3` / `zero_0030-fe0f-20e3`, `copyright_00a9-fe0f`, `registered_00ae-fe0f`.

**Формат item:**
```json
{ "name": "Русское название", "tags": "🔥 english name русское название", "figma": "Emoji/ComponentName",
  "file": "apple/slug_codepoints.png", "variants": [ { "label": "Google", "file": "google/slug_codepoints.png" } ] }
```
`tags` начинаются с самого эмодзи (поиск по символу), затем EN и RU название; `figma` — PascalCase, без пробелов, префикс `Emoji/`; `file` — всегда `apple/…`; `variants` опускать, если у Google нет картинки; у вариантов нет `type`.

**`emoji/custom.json`** — ручные добавления: `{ "<category-slug>": [ ...items ] }`, дедупликация по `file`, поддерживает `"insertAfter": "<filename-substring>"`. Ключ `symbols` не добавлять.

**Скрейпера в репозитории нет** (`scripts/scrape-emoji.js`, `extract-emoji.py`, `build-icons-data.js` удалены). Категории эмодзи поддерживаются вручную; `--rebuild-only` не существует — при необходимости скрейпер писать заново.

**Добавить эмодзи вручную:** PNG из шрифта Apple Color Emoji → кроп по bbox, 160×160 fit → `assets/emoji/pngs/apple/` → запись в `emoji/categories/<slug>.json` (и дублировать в `emoji/custom.json`) → `npm run build`.

# Build

**Никогда не править сгенерированное руками:** `logos/<cat>/<slug>/index.html`, блок `ECOSYSTEMS` в `js/data.js`, блок `RULES` в `tools/figma-plugins/typograf/code.js`, промо-блок в `ui.html` плагинов, всё между маркерами `START/END` — следующая сборка перетрёт. `.min.js`, `*.bundle.css`, `assets/og/*` — build-артефакты, коммитятся (деплой сборку не запускает).

## `npm run build`

Единственная точка входа для любого изменения контента (логотип, эмодзи, подборка, пост, общий шаблон/партиал). Делегирует `node scripts/build-all.js`, который запускает все шаги дочерними процессами в порядке зависимостей и встаёт на первой ошибке. **Порядок шагов — в `scripts/build-all.js` (он же источник правды); не дублируй его здесь.** Множество `▶ build-*.js` в логе — это сам `build-all.js`, а не ручной запуск.

- **Все шаги обязательны на каждом запуске; опциональных шагов и флагов-тиров нет** («slow tier» за `--og-home`/`--full` удалён). Опциональный шаг — забытый шаг. Все Puppeteer-шаги инкрементальны (сравнивают байты, пишут только изменившееся) — полная сборка без изменений ~74 с и без мусора в git. **Не возвращать опциональность:** дорого — оптимизируй шаг, а не убирай.
- `--dry-run` не пишет ничего ни в одном шаге.
- Отдельный скрипт оправдан, когда: отлаживаешь логику ОДНОГО скрипта (`--dry-run`-цикл), или правишь `build-og-images.js` сразу после добавления одного логотипа. Каждый скрипт работает и автономно.
- `publish-scheduled-posts.js` — единственная точка входа для публикации: прячет будущие посты, затем запускает `npm run build` (см. «Hosting & deploy»).
- **Тесты — каждый ловит свой класс поломки, любой падает — сборка встаёт:** `test-data`, `test-i18n`, `test-js`, `test-css-parity`, `test-html`, `test-links`, `test-component-wiring`, `test-dead-code`, `test-typograf-sync`, `test-ecosystem-sync` (подробности ниже). `--warn-only` у каждого снимает `exit 1`.
- **Правило для проверок:** проверка, не нашедшая ни одного объекта, обязана падать (SELF-CHECK), а не рапортовать успех.

## Типографика

- **`tools/figma-plugins/_shared/typograf-rules.js` — единственный источник правил** для сайта и Figma-плагина «Trace Typograf». Только чистые строковые функции; всё, что трогает узлы Figma, остаётся в `code.js` плагина. Правило правится ТОЛЬКО в источнике; вторую копию не заводить.
- **`build-figma-typograf.js`** запекает источник дословно в `tools/figma-plugins/typograf/code.js` между `// RULES:START` / `// RULES:END` (плагин в песочнице без `require()`). Маркеры ищутся строкой целиком (`^// RULES:END$`), не `indexOf` — заголовок источника упоминает эти же слова. **`test-typograf-sync.js`** сравнивает запечённый блок с ожидаемым байт в байт (общий `buildBlock()`), проверяет, что источник экспортирует всё нужное `scripts/lib/typograf.js` и не обращается к `figma.*`. Эти два шага — первые в `build-all.js`.
- **Третья копия движка** — `tools/extensions/trace-typograf/src/core/rules/*.js` (Chrome-расширение) — отстала на четыре правила и в единый источник НЕ переведена.
- **`apply-typography.js`** — auto-fix, а не тест: переписывает файлы на диске (русская типографика: НБСП, тире, «ёлочки», многоточие, номера/суммы). Первый шаг перед `test-data --pre`. Трогает только русский текст (никогда `_en` и EN-половину поста): `blog/posts/*.md` (`title`/`description` и RU-тело до `---EN---`; защищает код, инлайн-код, HTML-теги, `:::widget`, URL, маркеры списков, разделители таблиц), `logos/categories/*.json` (`about`, `desc`, `variants[].label`), `logos/labels.json`, `logos/category-seo.json` (`intro`, `title`, `h1`), `collections.json` (`title`/`h1`/`lead`, `intro[]`), `js/i18n-dict-ru.js` (только простые `'...'`-литералы на своей строке; после правки `node --check`, при ошибке файл откатывается целиком). **Не трогает** `name`/`tags`/`figma`/`file`/`ecosystem`/`alt_name` (НБСП в `tags` сломал бы поиск). Идемпотентен. Голые URL и «цифра:цифра» защищены отдельно (`URL_RE`/`RATIO_TIME_RE`) — движок иначе принял бы `://` и `:3` за смайлик и вставил пробел.
- **Состав конвейера у сайта и плагина разный осознанно** (`CONTENT_OPTS` против `DEFAULT_OPTS`): три правила плагина портят прозу сайта (заглавная после «:», чистка пробелов в скобках ломает каомодзи, `McDonald's → McDonald’s` — на 67 видимых мест, включается отдельным решением).
- **NBSP в JSON-полях:** `about`/`desc`/… содержат `\xa0` и `‑` (U+2011), которые не видны глазами, — `Edit` с обычными пробелами молча не совпадёт. Не перепечатывай кириллический текст в `old_string`/heredoc (на macOS ещё и NFC/NFD-порча): бери точное значение через `python3 -c "import json; print(repr(...))"`, дописывай к нему, пиши обратно прямой заменой по сырому тексту (не `json.dump` — перефоматирует файл). Новые предложения можно писать с обычными пробелами — `apply-typography.js` расставит НБСП.

## JS/CSS-минификация и бандлы

- **`build-js-minify.js`:** каждый `.js` в `js/` и `components/` → `<file>.min.js` рядом (terser); относительные и корне-абсолютные специфаеры на `.js` внутри переписываются на `.min.js`. **HTML ссылается на `.min.js`, не на исходник** — точки входа (`<script src>`, `type="module"`, `<link rel="modulepreload">`) прописаны вручную в `index.html`, `logos|emoji|icons/index.html`, `templates/*.html`, `templates/partials/*.html` и в `WIDGETS` в `scripts/build-blog.js`. Новая точка входа — сразу `.min.js`. Источник правды — неминифицированный файл; `.min.js` коммитится; правишь `js/foo.js` — прогони `npm run build`. Никакой тест не ловит рассинхрон источника и `.min.js`. Требует `terser`.
- **`build-js-bundles.js`:** перезаписывает `.min.js` **только точек входа** esbuild-бандлом (`bundle`, `format:'esm'`, `target:'es2022'`, minify) — граф из десятков модулей превращается в 3–4 запроса. Точки входа находит сам по `<script type="module" src="…min.js">` в готовом HTML + `templates/`. Строго после `build-js-minify.js`. Словари i18n остаются внешними (`EXTERNAL`): посетитель качает только свой язык. Остальные динамические импорты инлайнятся. Плагин `forceEsmModule` обязателен: файл без `import`/`export` esbuild считает CommonJS и оборачивает в не-async функцию, внутри которой top-level await из `js/i18n.js` даёт непарсящийся код при «успешной» сборке; плагин дописывает `export {}` при загрузке. `assertParses()` (`node --check` по `.mjs`) на каждом выходе — сборка встаёт при битом бандле; `logLevel` esbuild не `'silent'`. Требует `esbuild`.
- **`CLASSIC_BUNDLES`** (в том же файле, простая конкатенация `.min.js` через `;\n`): `components/lang-switcher.js`, `search-box.js`, `mobile-nav.js`, `cookie-consent.js` → `components/site-chrome.min.js`. Список задаётся руками. Подключаются на странице только через `templates/partials/nav-header.html` — единственный источник (раздаётся через `{{> nav-header}}` в 8 mustache-шаблонах, `build-tools-headers.js` в `tools/*.html` по маркерам `HEADER:START/END` и `build-home-sitemap.js` в `index.html`). Рукописные `logos|emoji|icons/index.html`, `terms/`, `consent/` — без синка: тег на `site-chrome.min.js` правь в каждой отдельно. `templates/category-page.html` не имеет `nav-header` (свой инлайн-хедер) и единственный источник cookie-consent для `logos/<cat>/` и `logos/ecosystem/<key>/`. **Новая страница с копипастой отдельного тега `cookie-consent.min.js` вместо `metrika.html`/`nav-header.html` снова станет лишним запросом.**
- **`build-css-bundles.js`:** склеивает наборы `css/*.css` в бандлы (`BUNDLES`, экспортируется; `main()` под `require.main === module`); исходники не трогает. `seo-page.bundle.css` — страницы логотипов/эмодзи/подборок; `catalog.bundle.css` — четыре страницы с `main.js`, намеренно надмножество (лишние селекторы дешевле лишних запросов). `@import` внутри бандла срезаются автоматически (`stripBundledImports` по списку `sources`).
- **`build-cache-bust.js`** — реально последний шаг: штампует `?v=ASSET_VERSION` во все ссылки на css/js/components во всех HTML.
- **`build-version.js`** пишет `js/version.js` (`ASSET_VERSION`, `YYYYMMDD`), его `utils.js` добавляет как `?v=` к каждому URL SVG/PNG/WebP логотипов и эмодзи. Значение должно быть стабильным между деплоями. Обязателен после замены существующего SVG/PNG под тем же именем или правки `/js`, `/css`; новый файл с новым именем сам меняет URL. `vercel.json` на проде не применяется (см. «Hosting & deploy»), `?v=` остаётся cache-buster'ом.

# Checkout «плати сколько хочешь»

Продукты (Chrome-расширения, далее плагины) не отдаются прямой ссылкой. Перед скачиванием модалка с полем суммы: **0 — валидная сумма** и главный сценарий (файл сразу, почту не спрашивают); платящему email нужен для invoice lava.top.

**Источник правды — `products.json`** (корень): `id`, `title`/`title_en`, `storageObject`, `downloadName`, `lavaOfferId`, общие `presets` по валютам. Текст модалки общий — в `js/i18n-dict-{ru,en}.js` (`pwyw*`, `thanks*`). Версия расширения — в `tools/extensions/<id>/manifest.json`.

**Файла нет в публичной раздаче.** `build-extension-zip.js` пишет архивы в `dist/products/` (gitignored), `scripts/sync-products.js` заливает их в приватный бакет Supabase Storage; единственный путь к файлу — подписанная ссылка на 15 минут от Edge Function `checkout` по токену заказа. **Не возвращай прямую ссылку на `.zip` в разметку** — ни в кнопку, ни в `downloadUrl` JSON-LD (там URL страницы продукта).

**Поток:** `[data-pwyw="<id>"]` на лендинге → `js/pwyw.js` (`css/pwyw.css`) → `POST /functions/v1/checkout` → **0**: заказ `free` → `/thanks/?t=<token>`; **>0**: invoice в lava.top → `paymentUrl` → возврат на `/thanks/?t=<token>` → `js/thanks.js` опрашивает статус до `paid`.

**Оплаченным заказ делает ТОЛЬКО вебхук `payment.success`.** Возврат браузера с lava.top ничего не доказывает и подделывается; `pending` на `/thanks/` — нормальное состояние.

**Таблицы** (`supabase/migrations/20260822000000_create_checkout.sql`): `products` (зеркало реестра; Edge Function не читает файлы репозитория) и `orders` (строка на каждое «Скачать», включая бесплатные). Отдельного счётчика нет: скачивания и суммы — агрегаты по `orders` (вкладка «Продукты» в `admin/index.html`, запрос на `/checkout` с `x-admin-key`).

**Секреты Supabase** (`supabase secrets set`, в репозиторий не попадают): `LAVA_API_KEY`, `LAVA_WEBHOOK_KEY`, `PRODUCTS_BUCKET`. Пока пусты `LAVA_API_KEY` или `lavaOfferId`, платный путь отвечает `503 payments_disabled`, бесплатный работает — штатный режим «платёжка ещё не подключена». Функция с `verify_jwt = false` (`supabase/config.toml`), как `track`/`suggest`.

**lava.top:** оффер должен быть опубликован с признаком «Цена по запросу через API», иначе `POST /api/v3/invoice` возьмёт цену оффера. Вебхук («Интеграции → API → Webhooks»): URL `<SUPABASE_URL>/functions/v1/checkout?action=webhook`, событие — оплата разового счёта, аутентификация — **«API key вашего сервиса»** со значением `LAVA_WEBHOOK_KEY` (функция проверяет заголовок `X-Api-Key`; Basic не подходит). Реальная схема API — `https://gate.lava.top/docs/documentation.yaml` (`developers.lava.top` — только обзоры; сторонние SDK неточны): `paymentMethod` в `POST /api/v3/invoice` принимает только `CARD|SBP|PAYPAL|PIX` и не передаётся (опционально, по умолчанию `CARD`); вебхук — `PurchaseWebhookLog`, `eventType` строго `payment.success`/`payment.failed`, `contractId` — id счёта. `GET /api/v2/products` по умолчанию отдаёт только `feedVisibility=ONLY_VISIBLE`: товар «Доступен по ссылке» ищи с `?feedVisibility=ALL`, его `offers[].id` — это `lavaOfferId`.

**Новый продукт:** запись в `products.json` → `node scripts/build-extension-zip.js` → `node scripts/sync-products.js` → кнопка `data-pwyw="<id>"` и `<script type="module" src="…/js/pwyw.min.js">` на лендинге. `sync-products.js` намеренно вне `build-all.js` (нужны сервисный ключ и сеть).

Статус: `gh run list --repo arturablyazov5-glitch/trace-logos --limit 5`, `curl -sI https://trace-logos.ru` (`server: GitHub.com`). Падающий параллельный `pages-build-deployment` — шум; смотри `Deploy to GitHub Pages`.

Флаги: `--dry-run`, `--all`, `--seed-only`. Не возвращай слепой пинг всего sitemap; новый шаг сборки, пишущий в каждую страницу неизменное по смыслу, — добавь его шаблон в `NOISE_RE`, а не переходи на `--all`. Ограничение: в CI скрипт пишет базу, но `deploy.yml` не коммитит её обратно, так что каждый запуск пингует всё, отличающееся от закоммиченной базы.
- **Скрипта `npm run deploy` нет** (удалён вместе с подсказками Vercel): деплой — это push по процедуре ниже, подсказки `scripts/publish-scheduled-posts.js` ведут на тот же поток commit → push → `restore`.
- Коммить и пушить только по просьбе пользователя; не напоминай «пора задеплоить».

## Процедура «запушить / выложить» (обязательна, без пропусков)

**Правило без исключений:** `blog/posts/*.md` с `date:` в будущем не должны быть доступны на trace-logos.ru и попадать в коммиты публичного репозитория — даже если «в этот раз механизм другой». Сборка дат не знает, `git add -A` коммитит всё дерево, поэтому перед КАЖДЫМ push, а не только когда есть пачка:

```bash
node scripts/publish-scheduled-posts.js status      # сколько постов впереди, есть ли активный hold
node scripts/publish-scheduled-posts.js --force     # hold + сборка. БЕЗ --force при отсутствии пачки на сегодня скрипт молча ничего не прячет
git add -A && git commit -m "..."
git push arturablyazov5 main                        # это и есть деплой
node scripts/publish-scheduled-posts.js restore     # ОБЯЗАТЕЛЬНО — иначе в рабочей копии не останется будущих постов
```

- Перед `git add`/`commit` проверь `git diff .gitignore` и `git status --porcelain`: `.blog-embargo-backup/` должен оставаться в `.gitignore` и не появляться в статусе; пропала строка — `git checkout -- .gitignore`.
- **Не коммить во время активного hold** (закоммитится удаление будущих постов); `hold` без `restore` оставляет копию без будущих постов; второй `hold` при активном `state.json` скрипт отклоняет. Не правь `.blog-embargo-backup/` руками (`status`, затем `restore`).
- После деплоя slug поста с будущей датой на проде обязан отвечать `404` (`curl -s -o /dev/null -w "%{http_code}" https://trace-logos.ru/blog/<slug>/`).

# Architecture Principles

**Модули.** Один модуль — одна забота (`color.js`, `search.js`, `virtual.js`, `export.js`…), не смешивать. Новая возможность — новый файл; не раздувать существующие. `main.js` — единственный оркестратор: владеет всеми DOM-ссылками, инициализирует модули, связывает события; модули не вызывают друг друга напрямую. Модуль отдаёт `init()`, получающий DOM-ссылки и колбэки от `main.js` (DI).

**Состояние.** Общее изменяемое состояние — в явных экспортируемых объектах (`colorState` в `color.js`), не разбросано по модулям. Без реактивных биндингов — DOM обновляется императивно (`classList`, `innerHTML`, `replaceChildren`).

**Данные.** Сервер — только статика. Текст SVG — источник правды для цветов и экспорта: всегда от сырого SVG, кэш `svgRawCache`. Цвета SVG нормализуются при загрузке (`normalizeSvgColors`), не при использовании.

**Рендеринг.** Виртуальный монтаж секций (overscan 900px) — не обходить `mountVirtualSection`/`unmountVirtualSection`. Высота сетки резервируется до монтажа. Картинки — `data-src` + `loadCardImage` при монтаже.

**CSS.** Один файл — одна забота (`color.css`, `cards.css`, `modals.css`…), не мешать несвязанные правила.

# Before touching any file

Перед правкой ответь:
1. **Есть ли готовый паттерн?** Проверь `components/`, `js/`, `css/`; если проект решает похожую задачу — следуй ему.
2. **Где источник правды?** Найди слой-владелец (HTML-шаблон, JS-модуль, JSON, CSS) и правь там, а не там, где всплыл симптом.
3. **Кого ещё это затрагивает?** Общий код (`main.js`, `utils.js`, компонент) — проверь все страницы, которые его используют (`logos/`, `emoji/`, `icons/`).

Поправили — значит чинил симптом; вернись к шагу 1.

# Debugging & Fix Philosophy

- Сначала корневая причина, потом фикс; чини в слое-владельце, не компенсируй в дочернем (фолбэки, заплатки, дублирующая логика, ветвление).
- Баг в карточке/панели — сначала данные (JSON → `data.js` → `main.js`), затем рендер, затем CSS.
- Правка в общем коде — проверь все затронутые страницы (logos, emoji, icons).
- Скептически относись к однофайловым фиксам: обоснуй, почему другие слои не затронуты. Предпочитай системный фикс, но соразмерно.
